<h2>Найпопулярніші запитання та відповіді на співбесіді з DevOps</h2>

<details>
<summary>1. Що таке DevOps?</summary>

#### DevOps

DevOps — це культура та практики, які об’єднують розробку і експлуатацію для
швидкої та надійної доставки змін.

**Коротко:**

- Спільна відповідальність Dev + Ops.
- Автоматизація і швидкий фідбек.
- Стабільні релізи з меншим ризиком.

</details>
<details>
<summary>2. Хто такий DevOps інженер?</summary>

#### DevOps

DevOps інженер будує CI/CD, IaC, моніторинг, керує середовищами і покращує
процеси доставки.

**Коротко:**

- Автоматизує шлях від коду до production.
- Зменшує ручну роботу і помилки.
- Працює на стику dev, ops і security.

</details>
<details>
<summary>3. Які основні принципи DevOps?</summary>

#### DevOps

Ключові принципи: collaboration, automation, continuous improvement,
observability, security by design.

**Коротко:**

- Часті невеликі зміни.
- Вимірюваність через метрики.
- Безперервне покращення процесу.

</details>
<details>
<summary>4. Як DevOps покращує процес доставки програмного забезпечення?</summary>

#### DevOps

DevOps прискорює релізи через CI/CD, автоматичні тести, стандартизацію і
моніторинг після деплою.

**Коротко:**

- Коротший release cycle.
- Вища якість і стабільність.
- Швидше відновлення після збоїв.

</details>
<details>
<summary>5. Які етапи життєвого циклу DevOps?</summary>

#### DevOps

Типово: Plan -> Code -> Build -> Test -> Release -> Deploy -> Operate ->
Monitor.

**Коротко:**

- Це безперервний цикл.
- Дані з Monitor повертаються в Plan.
- Автоматизація на кожному етапі.

</details>
<details>
<summary>6. Які основні переваги DevOps?</summary>

#### DevOps

Переваги: швидші релізи, менше інцидентів, краща взаємодія команд, нижчий MTTR.

**Коротко:**

- Швидкість + надійність.
- Прозорість процесів.
- Кращий time-to-market.

</details>
<details>
<summary>7. Як ви б впровадили DevOps у новому проєкті?</summary>

#### DevOps

Почав би з цілей і KPI, далі Git workflow, CI/CD, IaC, observability,
security checks, регулярні ретроспективи.

**Коротко:**

- Спочатку процес, потім інструменти.
- Pipeline as code + IaC.
- Постійне вимірювання результатів.

</details>
<details>
<summary>8. Чим DevOps відрізняється від Agile?</summary>

#### DevOps

Agile — про гнучку розробку продукту, DevOps — про доставку й експлуатацію змін
у production.

**Коротко:**

- Agile і DevOps доповнюють одне одного.
- Agile: що і як розробляти.
- DevOps: як стабільно постачати і підтримувати.

</details>
<details>
<summary>9. Які метрики (KPI) використовують для оцінки DevOps?</summary>

#### DevOps

Найчастіше — DORA: Deployment Frequency, Lead Time, Change Failure Rate, MTTR.

**Коротко:**

- Міряємо швидкість і надійність одночасно.
- KPI мають бути прив’язані до бізнес-цілей.
- Метрики потрібні для покращень, не для формальності.

</details>
<details>
<summary>10. Чому DevOps став таким популярним останніми роками?</summary>

#### DevOps

Через потребу бізнесу швидко випускати зміни без втрати якості, плюс розвиток
cloud, containers, IaC і CI/CD інструментів.

**Коротко:**

- Ринок вимагає швидкості.
- Технології зробили automation доступною.
- DevOps став стандартом delivery.

</details>
<details>
<summary>11. Які існують анти-патерни DevOps?</summary>

#### DevOps

Анти-патерни: ручні деплої, слабкі тести, відсутність ownership, DevOps як
«окремий відділ», відкладена безпека.

**Коротко:**

- Інструменти без культури не працюють.
- Ручні кроки = ризик помилок.
- Security має бути в процесі з початку.

</details>
<details>
<summary>12. Що означає концепція `Shift Left` у DevOps?</summary>

#### DevOps

Shift Left — перенос перевірок якості й безпеки на ранні етапи розробки.

**Коротко:**

- Раніше знайдена помилка дешевша.
- Тести і скани запускаються в CI.
- Менше дефектів у production.

</details>
<details>
<summary>13. Що таке `Continuous Testing`?</summary>

#### DevOps

Continuous Testing — автоматичні перевірки на всіх етапах pipeline, а не лише
перед релізом.

**Коротко:**

- Постійний фідбек про якість.
- Швидке виявлення регресій.
- База для стабільного CI/CD.

</details>
<details>
<summary>14. Що таке `Test Automation`?</summary>

#### DevOps

Test Automation — автоматизація запуску та перевірки тестів (unit,
integration, e2e тощо).

**Коротко:**

- Менше ручної роботи.
- Повторювані результати.
- Безпечні часті релізи.

</details>
<details>
<summary>15. Що таке `ChatOps`?</summary>

#### DevOps

ChatOps — виконання операційних дій через чат-ботів та інтеграції в командних
чатах.

**Коротко:**

- Швидка координація під час інцидентів.
- Прозорий журнал дій.
- Зручний командний інтерфейс.

</details>
<details>
<summary>16. Як би ви оцінили свій рівень знань Linux?</summary>

#### DevOps

Впевнений advanced рівень: адміністрування, troubleshooting, процеси, мережа,
systemd, shell automation.

**Коротко:**

- Сильний production-досвід.
- Орієнтація на root cause.
- Автоматизація типових операцій.

</details>
<details>
<summary>17. Які команди Linux ви використовуєте найчастіше?</summary>

`ls`, `find`, `grep`, `awk`, `sed`, `tail`, `journalctl`, `systemctl`, `ss`,
`ps`, `top/htop`, `df`, `du`, `chmod`, `chown`.

**Коротко:**

- Файли, логи, процеси, мережа.
- Базовий набір для щоденної роботи.
- Комбінації команд для швидкої діагностики.

</details>
<details>
<summary>18. Як перевірити використання CPU у Linux?</summary>

#### DevOps

`top`/`htop`, `mpstat`, `ps --sort=-%cpu`, `sar -u`, `uptime` для load average.

**Коротко:**

- Швидкий старт: `top`.
- Деталізація: `mpstat`, `sar`.
- Дивимось і %CPU, і контекст навантаження.

</details>
<details>
<summary>19. Як перевірити використання дискового простору?</summary>

#### DevOps

`df -h` для файлових систем, `du -sh` і `find -size` для пошуку великих файлів,
`df -i` для inode.

**Коротко:**

- `df` показує де проблема.
- `du/find` показують причину.
- Перевіряйте також inode.

</details>
<details>
<summary>20. Як знайти останніх користувачів, які входили в систему?</summary>

#### DevOps

`last`, `lastlog`, `w`, `who`.

**Коротко:**

- `last` для історії входів.
- `w/who` для активних сесій.
- Корисно для аудиту і розслідувань.

</details>
<details>
<summary>21. Як переглядати логи в Linux?</summary>

#### DevOps

Для systemd: `journalctl`; для файлів: `tail -f`, `less`, `grep`.

**Коротко:**

- `journalctl -u <service> -f` для live-аналізу.
- Фільтруйте за часом/рівнем/помилками.
- Централізований логінг обов’язковий у production.

</details>
<details>
<summary>22. Як керувати правами доступу до файлів?</summary>

#### DevOps

`chmod`, `chown`, `chgrp`, `umask`; за потреби ACL (`setfacl/getfacl`).

**Коротко:**

- Права + власник + група.
- Принцип least privilege.
- ACL для тонкої грануляції доступу.

</details>
<details>
<summary>23. У чому різниця між `systemctl start` та `systemctl enable`?</summary>

#### DevOps

`start` запускає сервіс зараз, `enable` вмикає автозапуск при boot.

**Коротко:**

- `start` = негайний запуск.
- `enable` = запуск після перезавантаження.
- Часто використовують `enable --now`.

</details>
<details>
<summary>24. Як моніторити продуктивність системи в Linux?</summary>

#### DevOps

CPU, RAM, disk I/O, network: `top`, `vmstat`, `iostat`, `ss`, `sar`, плюс логи
і алерти у централізованій системі.

**Коротко:**

- Локальні утиліти для діагностики.
- Централізований моніторинг для масштабу.
- Метрики + логи + алерти.

</details>
<details>
<summary>25. Що таке система контролю версій (VCS)?</summary>

#### DevOps

VCS зберігає історію змін коду, авторів змін і дозволяє повертатися до попередніх
станів.

**Коротко:**

- Історія змін і аудит.
- Командна робота без втрат.
- Основа сучасної розробки.

</details>
<details>
<summary>26. Які переваги використання систем контролю версій?</summary>

#### DevOps

Rollback, branching, code review, traceability, інтеграція з CI/CD.

**Коротко:**

- Безпечна командна робота.
- Прозора історія змін.
- Швидші і керовані релізи.

</details>
<details>
<summary>27. У чому різниця між централізованими та розподіленими VCS?</summary>

#### DevOps

Централізовані мають один сервер істини; розподілені (Git) дають повну локальну
копію історії кожному розробнику.

**Коротко:**

- Centralized: сильна залежність від сервера.
- Distributed: офлайн-робота і вища гнучкість.
- Git — стандарт distributed підходу.

</details>
<details>
<summary>28. Що таке Git?</summary>

#### DevOps

Git — розподілена система контролю версій для швидкого branching, merging і
спільної розробки.

**Коротко:**

- De facto стандарт VCS.
- Потужна робота з історією.
- База для PR-процесу.

</details>
<details>
<summary>29. Що робить команда `git clone`?</summary>

#### DevOps

Копіює віддалений репозиторій локально разом із історією та налаштовує `origin`.

**Коротко:**

- Створює локальну копію repo.
- Завантажує коміти і гілки.
- Готово до подальшої роботи.

</details>
<details>
<summary>30. Як запушити код у GitHub?</summary>

#### DevOps

`git add` -> `git commit` -> `git push origin <branch>`; далі відкривається PR.

**Коротко:**

- Commit в локальній гілці.
- Push у remote гілку.
- Merge через review.

</details>
<details>
<summary>31. Що таке `bare repository`?</summary>

#### DevOps

Bare repo — Git-репозиторій без робочої директорії, використовується як серверний
remote.

**Коротко:**

- Без working tree.
- Для push/pull, не для редагування.
- Типовий формат центрального repo.

</details>
<details>
<summary>32. Що таке `git stash`?</summary>

#### DevOps

Тимчасово зберігає незакомічені зміни, щоб переключитися на іншу задачу.

**Коротко:**

- «Відкласти» поточні зміни.
- Повернути через `stash pop/apply`.
- Корисно для швидкого контекст-switch.

</details>
<details>
<summary>33. Що таке гілкування (`branching`) у Git?</summary>

#### DevOps

Branching — ізольована лінія розробки для фіч/фіксів без впливу на основну
гілку.

**Коротко:**

- Паралельна робота команди.
- Безпечно для main.
- Feature branch -> PR -> merge.

</details>
<details>
<summary>34. У чому різниця між `git merge` та `git rebase`?</summary>

#### DevOps

`merge` зберігає історію злиття, `rebase` переписує історію в лінійний вигляд.

**Коротко:**

- `merge` безпечніший для shared history.
- `rebase` робить історію чистішою.
- Не rebasing публічні гілки.

</details>
<details>
<summary>35. Що таке `merge conflict` і як його вирішити?</summary>

#### DevOps

Конфлікт виникає, коли Git не може автооб’єднати зміни. Треба вручну обрати
правильний варіант, прибрати маркери і завершити merge/rebase.

**Коротко:**

- Конфлікт = неоднозначність змін.
- Вирішення вручну + `git add`.
- Часті синхронізації зменшують конфлікти.

</details>
<details>
<summary>36. Що таке `git bisect`?</summary>

#### DevOps

Інструмент binary search для пошуку коміту, що спричинив регресію.

**Коротко:**

- Швидкий пошук «поганого» коміту.
- Добре для складних багів.
- Працює вручну або зі скриптами.

</details>
<details>
<summary>37. У чому різниця між `git fetch` і `git pull`?</summary>

#### DevOps

`fetch` тільки завантажує зміни з remote, `pull` робить fetch і одразу інтегрує
у поточну гілку.

**Коротко:**

- `fetch` безпечний попередній крок.
- `pull` одразу змінює локальну гілку.
- Для контролю часто спочатку `fetch`.

</details>
<details>

`git show --name-only <sha>` або `git diff-tree --name-only -r <sha>`.

- Найпростіше через `git show`.
- Підходить для аудиту комітів.
- SHA гарантує точність.

</details>

**Коротко:**

<details>
<summary>41. Що таке `CI/CD`?</summary>

#### DevOps

CI/CD — автоматизація інтеграції, тестування і доставки змін до середовищ.

**Коротко:**

- Менше ручних кроків.
- Швидші релізи.

<details>
<summary>42. Які етапи має `CI/CD pipeline`?</summary>

#### DevOps

Source -> Build -> Test -> Package -> Deploy -> Verify -> Promote/Rollback.

**Коротко:**

- Кожен етап має quality gate.
- Pipeline має бути repeatable.

</details>
<details>
<summary>43. Що таке `Continuous Delivery`?</summary>

#### DevOps

Зміни автоматично готуються до релізу, але production-деплой зазвичай
затверджується вручну.

**Коротко:**

- Завжди release-ready стан.
- Контрольований випуск у production.
- Менший ризик великих релізів.

</details>
<details>
<summary>44. Що таке `Continuous Deployment`?</summary>

#### DevOps

Кожна зміна, що пройшла всі перевірки, автоматично деплоїться у production.

**Коротко:**

- Максимальна швидкість delivery.
- Потребує сильних тестів.
- Критичні моніторинг і rollback.

</details>
<details>
<summary>45. Що таке `Blue-Green deployment`?</summary>

#### DevOps

Два однакові середовища: активне і нове. Після перевірки трафік перемикається
на нове.

**Коротко:**

- Безпечне перемикання релізу.
- Мінімальний downtime.
- Швидкий rollback на попереднє середовище.

</details>
<details>
<summary>46. Що таке `Canary deployment`?</summary>

#### DevOps

Нова версія поступово отримує частину трафіку; при стабільних метриках rollout
розширюється.

**Коротко:**

- Поетапний реліз.
- Менший blast radius.
- Рішення на основі метрик.

</details>
<details>
<summary>47. Які best practices існують для CI/CD pipeline?</summary>

#### DevOps

Pipeline as code, швидкі тести, immutable artifacts, security scanning,
захищені гілки, environment parity, чіткі quality gates.

**Коротко:**

- Швидко, прозоро, відтворювано.
- Якість і security вбудовані.
- Маленькі зміни — краща стабільність.

</details>
<details>
<summary>48. Які проблеми можуть виникнути під час впровадження CI/CD?</summary>

#### DevOps

Flaky тести, довгі pipeline, різниця середовищ, слабка культура review,
некеровані секрети, відсутність ownership.

**Коротко:**

- Технічні й культурні проблеми пов’язані.
- Без стабільних тестів довіри до pipeline не буде.
- Впроваджувати краще поетапно.

</details>
<details>
<summary>49. Як забезпечити безпеку CI/CD pipeline?</summary>

#### DevOps

Least privilege, vault для секретів, SAST/SCA/скан образів, підпис артефактів,
захист гілок, ізоляція runner-ів, аудит.

**Коротко:**

- Security на кожному етапі pipeline.
- Контроль доступів і секретів — пріоритет.
- Supply chain security обов’язкова.

</details>
<details>
<summary>50. Як виконати `rollback` деплойменту?</summary>

#### DevOps

Зупинити rollout, повернути трафік/версію на last known good release,
перевірити health, провести RCA.

**Коротко:**

- Rollback має бути автоматизований.
- Потрібні immutable артефакти.
- Після відкату — аналіз причини.

</details>
<details>
<summary>51. Як побудувати та опублікувати Docker-образ у CI/CD pipeline?</summary>

#### DevOps

`docker build` -> тести/скани -> `docker login` -> `docker push` з versioned tag
(краще SHA), далі deploy цим тегом.

**Коротко:**

- Build, verify, push, deploy.
- Не покладатися лише на `latest`.

**Коротко:**

- Відповідальність ділиться між AWS і клієнтом.
- Чим ближче до IaaS, тим більше відповідальності у клієнта.
- Неправильна конфігурація клієнта залишається ризиком клієнта.

- Краща безпека (менше зайвих залежностей).

</details>

<details>
<summary>100. Що таке Kubernetes?</summary>

#### DevOps

Kubernetes (K8s) — платформа оркестрації контейнерів для автоматичного
розгортання, масштабування і керування containerized застосунками.

**Коротко:**

- Декларативне керування контейнерними workload.
- Автоматизує scaling, self-healing і rollout.
- De facto стандарт container orchestration.

</details>
<details>
<summary>101. Які проблеми вирішує Kubernetes?</summary>

#### DevOps

Kubernetes вирішує: оркестрацію контейнерів у кластері, service discovery,
автовідновлення pod-ів, балансування трафіку, rolling updates/rollback,
горизонтальне масштабування.

**Коротко:**

- Знімає ручне керування контейнерами в масштабі.
- Покращує надійність і repeatability релізів.
- Спрощує операції для мікросервісної архітектури.

</details>
<details>
<summary>102. Що таке `Pod`?</summary>

#### DevOps

Pod — найменша deployable одиниця в Kubernetes, яка містить один або кілька
контейнерів зі спільними network namespace і volumes.

**Коротко:**

- Pod = runtime-обгортка для контейнерів.
- Контейнери в pod ділять IP/port space.
- Зазвичай один основний контейнер на pod.

</details>
<details>
<summary>103. Що таке `Deployment`?</summary>

#### DevOps

Deployment — контролер Kubernetes для декларативного керування stateless
застосунками: створення/оновлення pod-ів, rollout, rollback і desired state.

**Коротко:**

- Керує життєвим циклом pod-ів через ReplicaSet.
- Підтримує rolling update і rollback.
- Основний об’єкт для app deployment.

</details>
<details>
<summary>104. Що таке `ReplicaSet`?</summary>

#### DevOps

ReplicaSet гарантує, що задана кількість однакових pod-ів постійно працює.
Зазвичай створюється і керується Deployment-ом.

**Коротко:**

- Підтримує потрібну кількість реплік.
- Автоматично відновлює втрачені pod-и.
- Рідко керується напряму у production.

</details>
<details>
<summary>105. Які типи `Services` існують у Kubernetes?</summary>

#### DevOps

Основні типи Service: `ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName`.
Також використовується headless service (`clusterIP: None`).

**Коротко:**

- `ClusterIP` — внутрішній доступ у кластері.
- `NodePort/LoadBalancer` — зовнішній доступ.
- `ExternalName` — DNS-аліас на зовнішній сервіс.

</details>
<details>
<summary>106. Що таке `Headless Service`?</summary>

#### DevOps

Headless Service — service без віртуального ClusterIP (`clusterIP: None`), який
повертає DNS-записи напряму на pod-и (часто для stateful workload).

**Коротко:**

- Немає єдиного service IP.
- DNS резолвиться в IP конкретних pod-ів.
- Часто використовується з StatefulSet.

</details>
<details>
<summary>107. Як Kubernetes додаток взаємодіє із зовнішнім світом?</summary>

#### DevOps

Через Service типу `LoadBalancer`/`NodePort`, Ingress Controller, API Gateway,
або service mesh/egress rules для вихідного трафіку.

**Коротко:**

- Вхід: Ingress або LoadBalancer service.
- Вихід: egress через CNI/мережеві політики/NAT.
- Безпечність забезпечують TLS, auth, network policies.

</details>
<details>
<summary>108. Що таке `Ingress`?</summary>

#### DevOps

Ingress — Kubernetes-ресурс для L7-маршрутизації HTTP/HTTPS трафіку до service
(за host/path правилами), який працює через Ingress Controller.

**Коротко:**

- Єдина точка входу для веб-трафіку.
- Підтримує host/path routing і TLS termination.
- Потребує встановленого Ingress Controller.

</details>
<details>
<summary>109. Як масштабувати додатки у Kubernetes?</summary>

#### DevOps

Основні підходи: ручне масштабування (`kubectl scale`), Horizontal Pod
Autoscaler (HPA), Vertical Pod Autoscaler (VPA), Cluster Autoscaler для вузлів.

**Коротко:**

- HPA масштабує pod-и за метриками.
- Cluster Autoscaler додає/прибирає nodes.
- Потрібні коректні requests/limits і метрики.

</details>

#### DevOps

Helm — пакетний менеджер Kubernetes, який використовує charts (шаблони) для
параметризованого і повторюваного розгортання застосунків.

**Коротко:**

- Helm chart = шаблон інфраструктури/додатку для K8s.

- Добре підходить для стандартизації deployment-ів.

</details>

<summary>111. Як діагностувати `CrashLoopBackOff`?</summary>

#### DevOps

- Часті причини: помилка старту, probes, конфіг, ресурси.
- Далі виправлення і контрольний rollout.

</details>
